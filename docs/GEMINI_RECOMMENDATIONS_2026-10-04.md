# Решения по рекомендациям Gemini — 4 октября 2026

Источник: предоставленная владельцем MHTML-копия разговора
«Архитектурный аудит проекта Цитадель — Google Gemini».
Выводы сверены с EWS после выпуска 0.3.37. В разговоре нет проверяемого
построчного разбора этого выпуска; архитектурные утверждения требуют проверки.

## Что внедрено в 0.3.38

| Изменение | Подтверждённая проблема | Проверка |
| --- | --- | --- |
| Объединение повторных heartbeat старых агентов | `/heartbeat` переписывал `nodes.last_seen_at` на каждом опросе, хотя `/sync` уже ограничивал запись четырьмя минутами | Подписанный запрос агента 0.3.1 в workerd и локальном D1: обновление lease — 3 записанные строки с индексами, повтор — 0, следующий просроченный lease — 3 |
| Пауза D1 после известного суточного лимита | Повторные запросы и обслуживание продолжали обращаться к уже недоступной БД | Блокировка повторного обращения, автоматическое открытие в 00:00 UTC, раздельные ограничения чтения и записи, корректный unwrap batch |
| `Retry-After` и `retry_at` для Hub | Клиенту не сообщалось, когда можно повторить запрос | HTTP 503 с сохранением кода ошибки и временем сброса; telemetry/presence не превращают quota в общий HTTP 500 |
| Общая пауза API агента | Main loop, keepalive и переподключение SSH могли независимо повторять запросы во время quota | Реальный локальный HTTP-сервер: один ответ quota, ноль дополнительных запросов до дедлайна, успешное восстановление |
| Понятное состояние интерфейса | Ошибка центрального хранилища не позволяет определить состояние компьютеров | Интерфейс сообщает об отсутствии свежего состояния и показывает время повторной попытки, когда Hub его передал |

Heartbeat сохраняет формат ответа и прежнюю схему подписи. Offline recovery,
смена версии/возможностей записываются сразу;
`paused` и `revoked` сохраняют смысл. Изменения hardware/network/SSH по-прежнему
сохраняются сразу. Стабильные CPU/RAM метрики, как на существующем sync,
обновляются в D1 раз в четыре минуты. Пятиминутное окно связи сохраняется.

Пауза D1 хранится в памяти экземпляра Worker и привязана к binding БД. Она
может исчезнуть при замене isolate/binding; это оптимизация повторных обращений,
не гарантия глобального ограничения запросов. При write quota обычные SELECT
сохраняют доступность. Неизвестные типы SQL считаются записывающими запросами.
Transient overload и ошибка подписи не запускают паузу до полуночи.

Результаты заданий остаются в существующей дисковой очереди агента до
подтверждения Hub. Проверены повторное открытие файла очереди и последующая
отправка того же ответа. Задания и результаты не переносятся в volatile RAM.
Это не обещание exactly-once для всех внешних действий.

## Что уже есть в действующем проекте

- Ed25519: приватный ключ агента, подпись метода, полного маршрута,
  времени, request ID и SHA-256 тела; проверка зарегистрированным ключом.
  Подписанные результаты используют тот же протокол.
- Проверка отзыва узла и возраста подписи; современные агенты используют
  durable nonce в существующем Durable Object. Старые версии сохраняют
  прежний протокол, чтобы их можно было обновить.
- Персистентные задания, назначения и команды в D1. Hub передаёт работу
  агенту; локальное обращение к LM Studio выполняет агент. Утверждение о
  синхронном ожидании LM Studio внутри основного Hub не соответствует этому пути.
- Условные записи AI/network/hardware/presence/SSH, объединение одинаковых
  повторных ошибок и объединённый `/sync` уже сокращают операции.
- CI уже выполняет проверки зависимостей, Bandit, тесты Windows/Linux,
  пакетов и браузера. Добавлять параллельный дублирующий pipeline не требуется.

## Что нельзя переносить из примеров без изменений

| Предложение | Решение и причина |
| --- | --- |
| `StateAggregator` с `D1.batch()` и экономией 95–99% | Не переносить: D1 учитывает строки и индексы, а не число HTTP batch. Код сохраняет каждый heartbeat отдельно; вызов flush в каждом request не объединяет их во времени |
| Общий RAM buffer и `setInterval` в Workers | Не хранить так подтверждённую работу: isolate может быть уничтожен, таймер не обеспечивает выполнение между запросами. `unshift` после ошибки не делает RAM durable; очереди не ограничены |
| Только Merkle root вместо событий | Не заменять данные: хэш не позволяет восстановить события, результат или доказательство конкретной записи без сохранённых исходных данных |
| «Proof-of-Inference» через подпись output | Подпись подтверждает ключ отправителя и неизменность ответа. Она не доказывает запуск модели, правильность ответа или отсутствие галлюцинаций; владелец скомпрометированного ключа может подписать выдуманный результат |
| Новый модуль Ed25519 из разговора | Не вводить второй несовместимый протокол. Примеры raw import/export приватного Ed25519-ключа не соответствуют Web Crypto; склейка полей через `:` допускает неоднозначность. Проверка timestamp без сохранения nonce не предотвращает повтор в допустимом окне |
| Enrollment и ротация через KV get/put/delete | Не переносить: последовательность операций не атомарна, KV имеет eventual consistency. Возможны повторное использование токена, перезапись ключа другого agent ID, гонки ротации. Потеря ответа после смены ключа разъединяет Hub и клиента; пример держит ключи только в RAM |
| Спекулятивный draft/target роутер и ускорение 2–3x | Отложить: пересылка чернового текста не равна speculative decoding. Нужны поддержка принятия draft tokens/logits, совместимые модели/токенизаторы и измерения с учётом сетевой задержки |
| Переписать Hub на Go/Rust, перейти на gRPC/NATS/mTLS | Не выполнять без доказанной необходимости: дополнительные службы, расходы и миграция действующих агентов. Текущий подписанный HTTPS-протокол не требует такой замены для указанных исправлений |

## Следующие изменения при подтверждённой необходимости

1. Отделить живые метрики/связь в per-node Durable Objects с TTL и явным
   признаком давности. Перед переносом авторизации определить атомарный отзыв
   ключей, восстановление после сбоя и поведение при недоступности D1.
2. Оценивать ёмкость по Cloudflare Analytics, включая индексы, задачи, UI,
   логи, bootstrap и другие БД аккаунта. Планировать запас; batching не
   увеличивает тарифный лимит. Изменение тарифа — отдельное решение владельца.
3. Если нужна ротация ключей: сначала реализовать durable pending identity,
   проверку владения обоими ключами, атомарный compare-and-swap, идемпотентное
   подтверждение и восстановление после потери ответа. Затем проверять на
   одном управляемом узле. Не включать ежедневную ротацию на всей сети сразу.
4. К ускорению inference возвращаться после реального базового E2E,
   измерения latency и проверки возможностей LM Studio.

## Предел текущего результата

Изменения уменьшают повторные обращения и heartbeat writes; они не снимают
уже исчерпанный суточный лимит и не позволяют обойти проверку отзыва узла.
Локальные runtime/HTTP-тесты не означают PASS реального LM Studio или SSH E2E
на компьютерах владельца. После восстановления D1 нужно получить свежую
связь, подтвердить версии агентов и повторить эти два удалённых теста.
